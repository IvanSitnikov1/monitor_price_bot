### Обзор проекта

Telegram-бот для мониторинга цен товаров на Ozon, Wildberries и Avito.
Пользователь добавляет ссылку на общую корзину Ozon или Wildberries либо отдельное
объявление Avito. Бот сохраняет товары и историю цен, показывает карточки товаров,
отправляет уведомления об изменениях и позволяет выгрузить историю проверок в CSV.

- Для Ozon и Wildberries у пользователя хранится одна активная корзина на маркетплейс.
  Новая корзина заменяет предыдущую; история выбывших товаров сохраняется.
- Объявления Avito отслеживаются по отдельности и не заменяют друг друга.
- Добавление и обновление выполняются последовательно через очередь с приоритетами:
  пользовательское добавление имеет приоритет выше планового обновления.
- Планировщик запускает обновление в 7, 15 и 22 часа со случайной задержкой до двух часов.
  Часовой пояс явно не задан в коде планировщика.
- Для каждого пользователя менеджер запускает отдельный Chrome с сохраняемым профилем
  и подключается к нему через Playwright по CDP. Авторизация Ozon и Wildberries
  выполняется при участии администратора.
- Предусмотрены персональные и общие для маркетплейса флаги техработ при блокировках,
  а также управление подписками и административная рассылка.

### Технологический стек

- Python >= 3.14; зависимости объявлены в `pyproject.toml`.
- aiogram 3 — Telegram Bot API, роутеры, клавиатуры и FSM с `MemoryStorage`.
- SQLite и aiosqlite — пользователи, товары, история цен, авторизации и подписки.
- Pydantic 2 и pydantic-settings — модели данных и настройки из `.env`.
- Playwright, playwright-stealth и Chrome/Chromium — получение данных со страниц.
- APScheduler — плановые обновления; asyncio — очередь и фоновые задачи.
- aiohttp — загрузка изображений; aiohttp-socks — поддержка прокси Telegram.
- В зависимостях также объявлены Selenium, webdriver-manager,
  undetected-chromedriver и curl-cffi; основной браузерный поток использует Playwright.

### Структура проекта

```text
run_bot.py              — точка входа: БД, очередь, планировщик, роутеры и polling
main.py                 — экземпляры Bot и Dispatcher, настройка прокси
config.py               — настройки приложения из .env
loggers.py              — настройка логирования
core/
  models.py             — модели Pydantic и перечисление маркетплейсов
  database.py           — схема SQLite, миграции и операции с данными
  parsing.py            — типизированные результаты парсинга
  task_repository.py    — транзакционное хранение и восстановление заданий очереди
handlers/
  common.py             — старт, помощь и просмотр подписки
  products.py           — приём ссылок и список позиций
  callbacks.py          — карточки, фильтры, удаление и история цен с CSV
  admin.py              — ручное обновление, рассылка и управление подписками
  auth/                 — согласие, запросы и авторизация Ozon и Wildberries
keyboards/              — обычные и inline-клавиатуры Telegram
utils/
  queue_worker.py       — очередь, синхронизация товаров и уведомления
  scraper.py            — парсинг корзин и объявлений, определение блокировок
  browser_manager.py    — процессы Chrome, пользовательские профили и вкладки
  price_updater.py      — постановка плановых обновлений в очередь
  maintenance.py        — файловые флаги техработ
  states.py             — состояния FSM
scripts/                — запуск Chrome, помощь с авторизацией и диагностика браузера
product_images/         — локальные изображения товаров по пользователям
STYLE.md                — обязательные правила оформления кода
DECISION.md             — журнал осознанных решений проекта
TASKS.md                — спецификации и статусы задач
```

Основной поток: обработчик Telegram → `TaskQueue` → парсер и `BrowserManager` →
SQLite → уведомление пользователя. Таблицы создаются и дополняются при запуске
через `setup_database()`; отдельного инструмента миграций нет.

Рабочие данные включают `bot_database.db`, браузерные профили, `product_images/` и
`maintenance_flags/`. Очередь хранится в таблице `queue_tasks` той же SQLite-базы:
принятое задание фиксируется до подтверждения пользователю, незавершённые задания
восстанавливаются при старте. Один воркер обслуживает один процесс бота.

Активные дубли объединяются, техработы откладывают задания без расходования попыток.
Временные ошибки допускают три запуска с паузами 60 и 300 секунд. Выполненные задания
не выбираются повторно; после аварии незавершённое задание может дать повторный замер.
Гарантированная доставка уведомлений и выполнение внешнего эффекта ровно один раз
не обеспечиваются. Состояния FSM хранятся только в памяти.

`QUEUE_FILE` (по умолчанию `queue_state.json`) используется только для однократного
импорта старой очереди. Импорт и отметка в `queue_imports` фиксируются транзакционно,
затем файл переименовывается в `.migrated`. Повреждённый файл сохраняется,
администратор получает сообщение об ошибке. Перед первым запуском обновлённой версии
следует сохранить резервную копию БД и старого файла очереди.

Запуск приложения: `python run_bot.py` из корня проекта после установки зависимостей
и настройки `.env`. Обязательная настройка — `BOT_TOKEN`; остальные настройки
определены в `config.py`. Для браузерного потока нужен установленный Chrome/Chromium.
Автоматические проверки: `.venv/bin/python -m unittest discover -s tests -p 'test_*.py'`.
Тесты используют временные БД, подменяют браузер и Telegram и не требуют реальных аккаунтов.

## Обязательные инструкции

Перед работой с явно выбранной задачей или прямым действием:

1. Полностью прочитай `STYLE.md`.
2. Полностью прочитай `DECISION.md`.
3. В `TASKS.md` прочитай только раздел выбранной задачи и необходимый контекст. Для
   прямого действия без выбранной задачи `TASKS.md` не читай без необходимости.

`TASKS.md` не нужно полностью перечитывать автоматически. Полный файл и старые задачи
читай только по прямой просьбе пользователя или если без них невозможно выполнить
явно выбранную задачу. При создании новой задачи можно прочитать только заголовки и
статусы, необходимые для выбора номера, не раскрывая историю.

Эти файлы являются обязательными инструкциями, а не справочными материалами. При
реализации задачи учитывай все действующие решения из `DECISION.md` и не нарушай их
без явной фиксации нового решения.

## Режимы работы

Режим работы определяется намерением пользователя:

- сообщение, начинающееся со слова `задача` без учёта регистра, запускает обработку;
- после слова `задача` могут идти двоеточие, точка или описание задачи;
- в тексте сообщения могу явно попросить начать задачу
- сообщение, начинающееся со слова `выполни` без учёта регистра, запускает
  непосредственное выполнение последнего согласованного плана без создания новой задачи
  в `TASKS.md`;
- после слова `выполни` можно указать конкретную задачу, номер или описание плана;
- если согласованный план отсутствует или его нельзя однозначно определить, запроси
  уточнение вместо самостоятельного выбора задачи.
- однозначная прямая просьба выполнить действие над проектом, например «измени»,
  «создай», «добавь», «исправь», «удали», «обнови» или «сделай», выполняется сразу без
  создания новой записи в `TASKS.md` и без спецификации `draft`;
- вопросы и обсуждение, например «как изменить» или «можно ли добавить», не запускают
  реализацию и не изменяют файлы;
- если формулировка может быть как просьбой, так и обсуждением, сначала запроси
  уточнение.

Пользователь может явно выбрать существующую задачу по номеру или названию. Не выбирай
задачу автоматически по её статусу. Несколько задач могут одновременно иметь статусы
`in_progress` или `draft`.

## Статусы и порядок работы

Допустимые статусы: `draft`, `in_progress`, `done`, `blocked`.

## Ротация TASKS.md

- Перед началом новой задачи или непосредственным выполнением согласованного плана
  проверяй количество строк в `TASKS.md`, не загружая весь файл в контекст.
- При достижении 5000 строк текущую задачу не прерывай. Сначала доведи выбранную задачу
  до завершения и зафиксируй её статус.
- После завершения задачи переименуй текущий файл в следующий архивный файл, например
  `TASKS-001.md`, создай новый чистый `TASKS.md` и укажи в нём ссылку на архив.
- Старые архивные файлы читай только по прямой просьбе пользователя или если они нужны
  для явно выбранной задачи.
- Если порог уже достигнут до начала новой задачи, выполни ротацию после завершения
  текущей выбранной задачи; при отсутствии такой задачи выполни её до добавления новой.

### Задача со статусом `draft`

До подтверждения пользователя:

1. Изучи код и текущее поведение системы, относящиеся к выбранной задаче.
2. Определи затрагиваемые файлы и риски.
3. Составь план реализации и полноценную спецификацию в формате из `TASKS.md`.
4. Обнови выбранный раздел `TASKS.md`, оставив статус `draft`.
5. Покажи спецификацию пользователю и остановись.

Изменять код или файлы реализации до подтверждения запрещено.

### Работа после подтверждения

1. Переведи выбранную задачу в `in_progress`.
2. Реализуй только утверждённый план.
3. Выполняй минимально необходимые изменения.
4. Не делай дополнительный рефакторинг и не меняй архитектуру без необходимости.

Перед изменением проверь существующую реализацию, связанные DTO, модели БД,
используемые эндпоинты и влияние на существующие модули. При выборе решения предпочитай
минимальные изменения, обратную совместимость и простую архитектуру.

## Definition of Done

Для задачи со спецификацией задача завершена только если:

- реализация выполнена;
- критерии готовности выполнены;
- выбранный раздел `TASKS.md` обновлён;
- перечислены изменённые файлы;
- описан способ проверки;
- статус задачи установлен в `done`.

Прямое действие завершено только если реализация выполнена, результат проверен и
пользователю передан итоговый отчёт. Новую запись в `TASKS.md` для прямого действия не
создавай, если пользователь явно этого не попросил.
