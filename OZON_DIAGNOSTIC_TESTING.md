# Проверка потери авторизации Ozon на сервере

Инструкция предназначена для диагностики пользователя, у которого после автоматического
обновления цен исчезает авторизация. Диагностика не запускает очередь, не обновляет базу
данных, не отправляет сообщения и не сохраняет значения cookies.

## Перед началом

1. Обновите проект до версии, содержащей `scripts/diagnose_ozon_session.py`.
2. Узнайте Telegram ID проблемного пользователя (`USER_ID` ниже).
3. Убедитесь, что бот запущен от того же системного пользователя, от имени которого будет
   выполняться диагностика.
4. Остановите бота и все Chromium-процессы, использующие профиль этого пользователя.
   Одновременный запуск запрещен общим lock-файлом.
5. Выполняйте этапы последовательно, не параллельно. Для чистого сравнения перед каждым
   этапом зафиксируйте, авторизован ли пользователь в обычном сценарии.

Не удаляйте `.monitor_price_bot.lock` вручную во время работы бота. Если lock занят, сначала
найдите и корректно остановите процесс-владелец.

## Включение диагностики

Флаг передается только конкретной команде и не изменяет постоянную конфигурацию. В командах
ниже используется `env OZON_DIAGNOSTICS_ENABLED=true`, поэтому отдельный `export` не требуется.
Если на сервере зависимости запускаются напрямую из virtualenv, замените `uv run python` на
`.venv/bin/python`.

## Этап 1: connect

Этап подключается к сохраненному профилю, проверяет PID, CDP-порт, профиль и cookies, но не
открывает страницу Ozon:

```bash
env OZON_DIAGNOSTICS_ENABLED=true \
  uv run python scripts/diagnose_ozon_session.py \
  --user-id USER_ID --stage connect
```

Код `3` означает, что cookies отсутствуют. Код `6` ожидаем, если cookies есть: без открытия
страницы состояние авторизации определить нельзя. Важен JSONL-отчет, а не только код shell.

## Этап 2: navigate

Этап выполняет один переход по сохраненной Ozon-корзине и ждет стабилизации страницы:

```bash
env OZON_DIAGNOSTICS_ENABLED=true \
  uv run python scripts/diagnose_ozon_session.py \
  --user-id USER_ID --stage navigate
```

Перед запуском желательно подтвердить, что сессия была авторизована. После завершения не
перезапускайте этап автоматически: он сам может воспроизвести проблему и изменить cookies.

## Этап 3: full

Этап имитирует полный сценарий обновления: stealth-настройки, поведение на странице,
ожидание сетевой стабилизации и контроль cookies/DOM. Изменения в базу не записываются:

```bash
env OZON_DIAGNOSTICS_ENABLED=true \
  uv run python scripts/diagnose_ozon_session.py \
  --user-id USER_ID --stage full
```

## Коды завершения

| Код | Результат | Значение |
| ---: | --- | --- |
| 0 | `session_preserved` | Авторизация сохранилась. |
| 1 | ошибка запуска | Lock, профиль, процесс браузера или другая операционная ошибка. |
| 2 | диагностика запрещена | Не установлен `OZON_DIAGNOSTICS_ENABLED=true`. |
| 3 | cookies отсутствуют/изменились | Сессия потеряна или UI стал анонимным. |
| 4 | `explicit_block` | Явная блокировка, HTTP 403 или блокирующий DOM-признак. |
| 5 | `network_or_dom_error` | HTTP 401, ошибка сети, загрузки или проверки DOM. |
| 6 | `auth_state_unknown` | Недостаточно признаков либо DOM-признаки противоречат друг другу. |

Код сам по себе не доказывает детект автоматизации. Для вывода используйте поля отчета
`result`, `browser_binding`, `cookie_diffs`, `navigation` и `auth_probes`.

## Где искать отчет

Отчеты создаются в закрытом каталоге:

```text
debug_data/ozon_auth_diagnostics/
```

Проверить последние файлы можно так:

```bash
ls -lt debug_data/ozon_auth_diagnostics | head
```

В отчете нет значений cookies, их хешей, Telegram ID, полного пути профиля, полного URL,
логина или текста исключения. Передавать нужно только JSONL-отчеты, не каталог `user_data/`.

## Как трактовать результаты

- `identity_mismatch` или ошибка запуска: проверить гонку процессов, закрытие старого
  Chromium, соответствие профиля и CDP-порта.
- `cookies_absent_before_navigation`: сессия уже отсутствовала до перехода; это не похоже
  на очистку во время обновления.
- `cookies_changed_after_navigation`: переход изменил или удалил cookies; сравнить время,
  HTTP-статусы и этап `full` с `navigate`.
- `anonymous_with_preserved_cookies`: cookies остались, но Ozon показал анонимный интерфейс;
  возможна серверная инвалидизация или антибот-проверка.
- `explicit_block`: есть явный блокирующий признак или 403; не менять одновременно порт,
  прокси и fingerprint.
- `network_or_dom_error`: сначала исключить нестабильный канал, таймауты и изменение верстки.
- `session_preserved`: проблема этим запуском не воспроизведена.
- `auth_state_unknown`: повторять запуск без изменения условий не следует; нужны логи
  обычного обновления и серверное сравнение по времени.

## Завершение проверки

После трех этапов запустите бота штатной командой сервиса. Переменная окружения из команд
выше действует только для отдельного процесса и не требуется при обычном запуске.

Зафиксируйте для каждого отчета время, этап и код завершения. Не удаляйте отчеты до их
анализа. Если потребуется повтор, сначала снова остановите бот и Chromium и отметьте,
была ли сессия авторизована перед запуском.
